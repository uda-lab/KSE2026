# INC-005: codex サイドプロセス残留による低メモリ cascade — 別プロジェクトで既知の教訓が横展開されず，対策直後に別形態で再発（OOM 帰属は 2026-07-31 再調査で訂正）

- **Incident ID:** INC-005
- **Date and environment:** 2026-07-18（残留チェーン蓄積の主因は 07-17 夜間のレビュー波），vps（cgroup メモリ上限 `memory.max`=3.42GiB・`memory.swap.max`=0 でコンテナは swap 不可．`free` の total 3.8Gi と Swap 2.0Gi は host 側の値で，host の /swapfile 2GiB は boot 起動時から常在 — 2026-07-31 再調査で明確化），`uda-lab/leray-hopf` の低優先度 issue 群を扱う継続オーケストレーション（session `de129390`，複数 worktree `wt-*` を並行運用）
- **Trigger:** 前日夜間の per-worktree codex 事前レビュー波が残した broker/app-server 常駐チェーン（1 レビューにつき 1 系統，60〜330MB，自動回収されない）の蓄積．そこへ (a) 前任 agent `issue155` を「死亡」と誤判定して後継 `issue155b` を同一 worktree に再 dispatch（実際は生存，~3h45m の二重稼働），(b) 後継が `.lake` ハードリンク共有規約を知らず mathlib 全量のコールドビルド（~1930 ファイル）を開始，という 2 つの負荷が重なった
- **Immediate symptom:** 重量級ビルドが終盤（1802/1851 ファイル等）で無言のまま反復死（task status は "killed"，コンパイルエラーなし，exit 137）．07:40Z 時点で `free` 196Mi・`available` 606Mi（used 3.2Gi/total 3.8Gi）まで枯渇
- **Underlying cause:** (1) codex プラグインのサイドプロセスが構造的に自動回収されない．(2) 「作業完了時にサイドプロセスを回収する」という教訓は 2026-05-09 に**別プロジェクト**の tmux pane 蓄積 OOM として既知で，当該プロジェクトの memory には記録済みだったが，失敗クラスの一般化（横展開）がされず，本プロジェクトの codex チェーンという別の具体形には適用されなかった（EV-0005 自身が「既知の教訓を横展開できていなかった」と明記）．(3) 監視の設計不備 — 可視の lean プロセス RSS（~850MB）だけを見て「OOM の危険なし」と誤診断し（06:28Z），隠れた常駐チェーン群と `available` を確認していなかった
- **Affected theorem, file, or campaign:** `LerayHopf/Torus/ConvectionExtension.lean` の検証ビルド（RSS >1.8GB，反復 OOM の直接対象），issue #154/#155/#156 の 3 トラック．証明成果物自体への影響はなし（同日中に PR #174/#175/#176 全てマージ）
- **Why existing checks failed:** ビルド失敗は「killed」としか現れず，コンパイルエラーと区別されないまま detached 再起動で握り潰された．オーケストレータの進捗確認は `used`/可視プロセス基準で，`available` と隠れ常駐プロセスを測っていなかった．cgroup の `oom_kill` カウンタはクライシス発覚まで一度も読まれていない
- **How the problem was detected:** オーケストレータの自発的監視ではなく，owner 起点である．owner の "status" は 07:32:21Z に送信されたが資源逼迫下で **8 分間配送されず**（07:40:09Z に配送．session は 06:34Z から idle），配送 3 秒後の 07:40:12Z に owner が **stale プロセス群の一括 kill を明示的に指示**した．`free -h` による枯渇検出（07:40:35Z，`available` 606Mi）はこの指示の後である．`readlink /proc/<pid>/cwd` による全チェーンの cwd 追跡で，merge 済み・削除済み worktree に紐づく残留（stale/orphaned）チェーン 14 系統（28 プロセス，~1〜1.5GB）を特定．`cat /sys/fs/cgroup/memory.events` の `oom_kill=7` は当時「反復 build 死はすべて kernel OOM killer の SIGKILL」の事後確定と解釈されたが，**この帰属は 2026-07-31 の host 側照合（issue #100）で否定された**（下記「2026-07-31 再調査による訂正」）
- **Recovery procedure:** owner の明示指示（07:40:12Z）に基づき残留（stale/orphaned）チェーン 14 系統を一括 kill（`available` 606Mi→2.2Gi）．ヘッドルーム最大（2.5Gi）で `flock /tmp/lean-build.lock` 下の再ビルドに成功．生存していた前任 `issue155` の所有権を回復し後継を `TaskStop`（二重稼働解消）
- **Permanent guardrail introduced:** 同日 07:47–07:51Z，owner の再犯指摘を受け **4 層**に恒常対策を記録: ①global memory（05-09 事案との再犯関係を明記），②③両プロジェクトの project memory，④`~/.claude/CLAUDE.md` へのコンテナ限定規約の直接注入（sweep・ビルド前 `available` ≥ 2GiB 確認・`.lake` ハードリンク共有・`flock` 直列化・dispatch prompt への明記・`LEAN_NUM_THREADS=1` 縮退）．④は「memory recall に依存した横展開が機能しなかった」という根本原因への対応として，recall 非依存の常時注入層へ意図的に移した
- **Generalisable lesson:** (1) エージェントが呼び出すツール（レビュー用 LLM CLI 等）の常駐サイドプロセスは，回収を構造化（作業完了時に必ず kill）しない限り蓄積し，メモリが最稀少資源の環境では OOM に直結する．(2) 教訓を「プロジェクト単位の記憶」に置くと失敗クラスの一般化が起きない — 同じ失敗が具体形を変えて別プロジェクトで再発する．(3) 対策は狙った経路（残留チェーン蓄積）の再発は止めたが，**同日午後に「正当な単一ビルドのピーク RSS ~1.9GB」という構造的に別の経路で同じ低メモリ症状が再発**した（12:42/13:06Z，残留チェーン 0・`oom_kill` 不変）．これを実害なく検知できたのは，個別対策ではなく同時に導入した計測規約（`used` でなく `available` で判断し閾値で報告）だった — 症状ベースの監視規約は原因別対策より汎化する．(4) AI エージェント × Lean/mathlib 開発は，単一モジュールのコンパイルだけで RSS ~1.9GB に達する上にエージェント基盤・レビューチェーンが常駐分を消費するため，~3.4GiB 級（cgroup 上限）のコンテナでは恒常的な資源管理そのものがオーケストレーションの一部になる — 潤沢なメモリは品質要件である．(5) **agent session 内部の観測だけで組み立てた因果診断は host 側一次記録と矛盾し得る** — 本件では累積 OOM counter を当日の build 死の機構確認と解釈したが，host kernel log との照合で counter は 2 日前の別事象に帰属し，当日の kill 機構は未特定と判明した（2026-07-31 訂正）．検出・回復経路の記述には session の観測境界の明示が要る
- **Primary evidence:** EV-0247（session `de129390` メイン transcript，07-18 区間 L6855〜L8065．`free -h`/`ps aux`/`readlink`/`memory.events` の生出力を含む），EV-0005（`feedback_reap_agent_side_processes.md`，07-18T07:50Z 作成 = 是正措置そのものの実物，05-09 先行事案と横展開失敗の自己記録），`evidence/session-index/de129390-559a-4ecd-950e-3667cf1c1c3c.md`（符号化 index），leray-hopf#174/#175/#176．2026-07-31 再調査分: KSE2026 issue #100 のコメント（host journald の kernel log・sudo 実行記録・systemd swap 記録・host shell history を read-only で照合した redacted summary．host 側 raw log は escrow 外）
- **Evidence type:** primary（cascade 本体・回復・恒常対策は EV-0247 の生出力で完結．EV-0005 は是正時に書かれた一次artifact）／一部 secondary（2026-05-09 の別プロジェクト先行事案は EV-0005 の記述と owner 報告（2026-07-23，issue #33）によるもので，当該プロジェクトの memory 実物は本 escrow 外）

## 2026-07-31 再調査（KSE2026 issue #100）による訂正

paper 執筆時の author 回想（「incident 当日に host 側から手動 kill して通信を回復させた」）
を契機に，host 側一次記録（journald の kernel log・sudo 実行記録・systemd swap 記録，
host shell history）と session transcript を read-only で照合した．redacted summary は
issue #100 のコメントに記録済み（host 側 raw log は escrow 外）．確定事項:

1. **incident 当日（07-18）に kernel OOM kill は 0 件**（global / memcg とも．当該 boot
   07-10〜07-21 の kernel log 全量で確認．userspace OOM デーモンも不在）．07:40Z 時点の
   cgroup 使用量は上限未到達（memory.current 3.32GiB < memory.max 3.42GiB）で，
   memcg OOM 不発生と整合する．
2. **`oom_kill=7` は 07-16T18:25〜21:54 JST の host global OOM ストームに帰属**．
   当該コンテナ cgroup 所属の victim 計 7 件（claude ×1，lean ×6）が host の
   global OOM killer に killed された kernel 記録があり，07-18T07:44Z に読まれた
   累積値 7 と正確に一致する．同ストームでは host user session 基盤
   （dbus / user 側 systemd）も killed され，VPS が実際に不安定化していた．
3. **当日の反復 build 死（exit 137）の kill 主体は未特定（unresolved）**．kernel OOM・
   userspace OOM デーモンとも否定済み．候補は agent harness による background task の
   kill（issue155/155b の二重稼働との関係を含む）だが，subagent transcript の
   forensics は未実施．
4. **author 回想の host-side kill は当日の記録に痕跡がない**（shell history・sudo・
   kernel 記録すべて）．history に残る kill 群は 2026-06-20（8 プロセス一括，sudo
   記録で日時確定）および 2026-05 上旬のもので，author も 06-20 事案との混線で
   あった可能性が高いことを確認した（issue #100 コメント）．よって本 card の
   detection / recovery 記述に host-side 介入は含めない．
5. **swap の明確化**: host /swapfile 2GiB は boot 起動時から常在（07-16 ストームは
   swap 存在下で host RAM+swap ごと枯渇して発生）．コンテナ cgroup は
   `memory.swap.max`=0 で swap 不可．session 内 `free` の Swap 表示は host 側の値．

この訂正に伴い，detection の actor attribution（owner の明示指示が検出に先行），
lesson (5)（session 観測境界），Confidence 欄を書き換えた．訂正前の記述は
git 履歴と issue #100 に保存されている．
