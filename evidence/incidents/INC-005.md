# INC-005: codex サイドプロセス残留による OOM cascade — 別プロジェクトで既知の教訓が横展開されず，対策直後に別形態で再発

- **Incident ID:** INC-005
- **Date and environment:** 2026-07-18（ゾンビ蓄積の主因は 07-17 夜間のレビュー波），vps（cgroup メモリ上限 `memory.max`=3.42GiB・swap 0 のコンテナ．`free` の total 表示は 3.8Gi だが実効上限は cgroup 側），`uda-lab/leray-hopf` の低優先度 issue 群を扱う継続オーケストレーション（session `de129390`，複数 worktree `wt-*` を並行運用）
- **Trigger:** 前日夜間の per-worktree codex 事前レビュー波が残した broker/app-server 常駐チェーン（1 レビューにつき 1 系統，60〜330MB，自動回収されない）の蓄積．そこへ (a) 前任 agent `issue155` を「死亡」と誤判定して後継 `issue155b` を同一 worktree に再 dispatch（実際は生存，~3h45m の二重稼働），(b) 後継が `.lake` ハードリンク共有規約を知らず mathlib 全量のコールドビルド（~1930 ファイル）を開始，という 2 つの負荷が重なった
- **Immediate symptom:** 重量級ビルドが終盤（1802/1851 ファイル等）で無言のまま反復死（task status は "killed"，コンパイルエラーなし，exit 137）．07:40Z 時点で `free` 196Mi・`available` 606Mi（used 3.2Gi/total 3.8Gi）まで枯渇
- **Underlying cause:** (1) codex プラグインのサイドプロセスが構造的に自動回収されない．(2) 「作業完了時にサイドプロセスを回収する」という教訓は 2026-05-09 に**別プロジェクト**の tmux pane 蓄積 OOM として既知で，当該プロジェクトの memory には記録済みだったが，失敗クラスの一般化（横展開）がされず，本プロジェクトの codex チェーンという別の具体形には適用されなかった（EV-0005 自身が「既知の教訓を横展開できていなかった」と明記）．(3) 監視の設計不備 — 可視の lean プロセス RSS（~850MB）だけを見て「OOM の危険なし」と誤診断し（06:28Z），隠れた常駐チェーン群と `available` を確認していなかった
- **Affected theorem, file, or campaign:** `LerayHopf/Torus/ConvectionExtension.lean` の検証ビルド（RSS >1.8GB，反復 OOM の直接対象），issue #154/#155/#156 の 3 トラック．証明成果物自体への影響はなし（同日中に PR #174/#175/#176 全てマージ）
- **Why existing checks failed:** ビルド失敗は「killed」としか現れず，コンパイルエラーと区別されないまま detached 再起動で握り潰された．オーケストレータの進捗確認は `used`/可視プロセス基準で，`available` と隠れ常駐プロセスを測っていなかった．cgroup の `oom_kill` カウンタはクライシス発覚まで一度も読まれていない
- **How the problem was detected:** オーケストレータの自発的監視ではなく，**owner の "status" 一言（07:40Z）を契機に** `free -h` が実行され枯渇（`available` 606Mi）が発覚した．`readlink /proc/<pid>/cwd` による全チェーンの cwd 追跡で，merge 済み・削除済み worktree に紐づくゾンビ 14 系統（28 プロセス，~1〜1.5GB）を特定．`cat /sys/fs/cgroup/memory.events` の `oom_kill=7` により，それまでの反復 build 死がすべて kernel OOM killer の SIGKILL だったと事後確定した
- **Recovery procedure:** ゾンビ 14 系統を一括 kill（`available` 606Mi→2.2Gi）．ヘッドルーム最大（2.5Gi）で `flock /tmp/lean-build.lock` 下の再ビルドに成功．生存していた前任 `issue155` の所有権を回復し後継を `TaskStop`（二重稼働解消）
- **Permanent guardrail introduced:** 同日 07:47–07:51Z，owner の再犯指摘を受け **4 層**に恒常対策を記録: ①global memory（05-09 事案との再犯関係を明記），②③両プロジェクトの project memory，④`~/.claude/CLAUDE.md` へのコンテナ限定規約の直接注入（sweep・ビルド前 `available` ≥ 2GiB 確認・`.lake` ハードリンク共有・`flock` 直列化・dispatch prompt への明記・`LEAN_NUM_THREADS=1` 縮退）．④は「memory recall に依存した横展開が機能しなかった」という根本原因への対応として，recall 非依存の常時注入層へ意図的に移した
- **Generalisable lesson:** (1) エージェントが呼び出すツール（レビュー用 LLM CLI 等）の常駐サイドプロセスは，回収を構造化（作業完了時に必ず kill）しない限り蓄積し，メモリが最稀少資源の環境では OOM に直結する．(2) 教訓を「プロジェクト単位の記憶」に置くと失敗クラスの一般化が起きない — 同じ失敗が具体形を変えて別プロジェクトで再発する．(3) 対策は狙った経路（ゾンビ蓄積）の再発は止めたが，**同日午後に「正当な単一ビルドのピーク RSS ~1.9GB」という構造的に別の経路で同じ低メモリ症状が再発**した（12:42/13:06Z，ゾンビ 0・`oom_kill` 不変）．これを実害なく検知できたのは，個別対策ではなく同時に導入した計測規約（`used` でなく `available` で判断し閾値で報告）だった — 症状ベースの監視規約は原因別対策より汎化する．(4) AI エージェント × Lean/mathlib 開発は，単一モジュールのコンパイルだけで RSS ~1.9GB に達する上にエージェント基盤・レビューチェーンが常駐分を消費するため，~3.4GiB 級（cgroup 上限）のコンテナでは恒常的な資源管理そのものがオーケストレーションの一部になる — 潤沢なメモリは品質要件である
- **Primary evidence:** EV-0247（session `de129390` メイン transcript，07-18 区間 L6855〜L8065．`free -h`/`ps aux`/`readlink`/`memory.events` の生出力を含む），EV-0005（`feedback_reap_agent_side_processes.md`，07-18T07:50Z 作成 = 是正措置そのものの実物，05-09 先行事案と横展開失敗の自己記録），`evidence/session-index/de129390-559a-4ecd-950e-3667cf1c1c3c.md`（符号化 index），leray-hopf#174/#175/#176
- **Evidence type:** primary（cascade 本体・回復・恒常対策は EV-0247 の生出力で完結．EV-0005 は是正時に書かれた一次artifact）／一部 secondary（2026-05-09 の別プロジェクト先行事案は EV-0005 の記述と owner 報告（2026-07-23，issue #33）によるもので，当該プロジェクトの memory 実物は本 escrow 外）
- **Confidence of reconstruction:** high（タイムライン・件数・メモリ数値はすべて transcript 内の生コマンド出力で裏付け）．ただし `oom_kill=7` はコンテナ起動以降の累積カウンタで，個々の kill のタイムスタンプは取得不能（dmesg 不可）のため，7 件全てが本 cascade 中である保証はない — 「本セッションの反復 build 死が OOM だった」ことの確定には十分だが，件数の帰属は保守的に扱う

## 経緯（詳細）

1. **2026-07-17 夜間（伏線）:** worktree ごとの codex 事前レビュー波が実行され，レビュー
   1 件につき broker/app-server 常駐チェーン 1 系統（60〜330MB）が回収されないまま残置
   された．後に kill される 14 系統中 13 系統がこの夜のものと特定される．
2. **07-18T04:00Z:** 前任 agent `issue155` が長時間無応答（`TaskOutput` も "No task
   found"）のため死亡と判定され，後継 `issue155b` が**同一 worktree** `wt-155` に
   dispatch された．実際には前任は生存しており，以後 ~3h45m の二重稼働となる
   （WT-CONFLICT）．後継は `.lake` ハードリンク共有規約を知らされておらず，
   mathlib をソースからコールドビルドし始めた．
3. **~06:00Z:** そのビルドが 1802/1851 ファイル地点で無言のまま死亡（"killed"，
   エラーなし）．原因を確認しないまま detached（setsid+nohup+disown）で再起動された．
4. **06:28–06:31Z（誤診断）:** オーケストレータは進捗確認時に lean プロセス RSS
   ~850MB のみを見て「ヘッドルーム十分，OOM の危険なし」と報告した．未回収チェーン群
   と `available` は確認されていない．
5. **07:40Z（発覚）:** owner の "status" 一言を契機に `free -h` が実行され，
   `free` 196Mi・`available` 606Mi（used 3.2Gi/total 3.8Gi）の枯渇が初めて
   検出された．
6. **07:41–07:42Z（特定と回復）:** 全 codex チェーンの cwd を `readlink
   /proc/<pid>/cwd` で追跡し，merge 済み・削除済み worktree に紐づくゾンビ 14 系統
   （28 プロセス，~1〜1.5GB）を特定・一括 kill．`available` は 2.2Gi へ回復
   （稼働中の 1 系統のみ意図的に残置）．
7. **07:44Z（事後確定）:** `memory.events` の `oom_kill=7` により，反復 build 死は
   すべて kernel OOM killer の SIGKILL と確定．直近の試行は mathlib ~1930 ファイルを
   完走した後，target module 本体（RSS >1.8GB）のコンパイル中——つまり最も高くついた
   地点——で殺されていた．
8. **07:46Z:** ヘッドルーム最大（2.5Gi）で `flock` 直列化の下に再ビルドし成功．
   前任 `issue155` の生存確認（独自に `.lake` 共有を構築し triage 39 件完了済み）と
   後継の停止により二重稼働を解消．
9. **07:47–07:51Z（恒常対策）:** owner が「同種の放置 OOM は数回目」と再犯を指摘．
   2026-05-09 に別プロジェクトで tmux pane 蓄積により同クラスの OOM が発生し，教訓は
   当該プロジェクトの memory に記録済みだったが，本プロジェクトの codex チェーンという
   別の具体形には横展開されていなかった．対策は global memory・両プロジェクトの
   project memory・`~/.claude/CLAUDE.md` 直接注入の 4 層に記録され，特に④は
   「recall 依存の横展開は機能しない」という診断に基づき常時注入層へ移された．
10. **12:42Z / 13:06Z（別形態での再発）:** 対策導入後，`issue154` の downstream
    検証ビルド（`AubinLionsLimitPassage.lean`，1539 行・依存最多，`LEAN_NUM_THREADS=1`，
    RSS ~1.9GB）で `available` が 2 度 1.9GiB まで低下した．sweep はゾンビ 0，
    `oom_kill` は 7 のまま——つまり対策が狙った経路ではなく，**正当な単一ビルドの
    ピーク RSS という構造的に別の経路**で同じ症状が再発した．同時に導入されていた
    「`available` 基準・閾値報告」の計測規約に agent が従って自発報告したため，
    実害なく確認のみで通過した．
11. **13:10Z（規約の定着確認）:** `issue154` が PR #176 マージ後に worktree 削除・
    自身の codex チェーン kill・branch 整理まで新規約どおりに完遂（同日中に規約が
    実装 agent レベルで一巡した）．セッション終了（~13:19Z）まで新規 OOM なし．
    同日 PR #174/#175/#176 がマージされ，形式化作業自体への恒久的損害はなかった．
