# INC-003: ログローテーションによる研究記録（創成期セッションログ）の不可逆喪失

- **Incident ID:** INC-003
- **Date and environment:** 2026-06-10〜07-21（喪失発生は 2026-07 中旬と推定），local-secondary（削除発生地点として有力）／全 host（影響），leray-hopf 全体
- **Trigger:** Claude Code の既定設定 `cleanupPeriodDays = 30` によるセッションログの自動削除．研究記録の保全要件を検討しないままツール既定値で運用を開始した
- **Immediate symptom:** Phase 1 収集（2026-07-20〜21）時点で，repo init（06-10，27 commits）〜06-14 のセッションログが**どの host にも存在しない**
- **Underlying cause:** research-record retention をツール既定値に委ねたこと．加えて「どのマシンにいつログが存在したか」の台帳が事後まで存在せず，喪失の発生自体が収集時まで検知されなかった
- **Affected theorem, file, or campaign:** C0 Bootstrap 期（06-10〜06-11，27+1 commits）と休止期（06-12〜14）の全セッション．形式化成果物自体への影響はない（Git は完全）が，**「27 commits の init 日に何をどう指示したか」という一次プロセス記録が消失**
- **Why existing checks failed:** 当時ログ保全のチェック自体が存在しなかった（本プロジェクト＝論文側の evidence 保全体制は 07-20 の Phase 0 で初めて構築された）
- **How the problem was detected:** Phase 1 inventory で最古セッションが 06-15（local-secondary）であることが判明し，git 密度分析（init 06-10）との突合で欠損として確定
- **Recovery procedure:** VPS の 07-10 インフラスナップショットから復元を試行（issue #15）．結果は**負**: バックアップは現行 escrow の真部分集合であり，ローテーション非対象の global prompt history（04-26 まで遡及）により「VPS 上の leray-hopf 作業は 06-19 開始．06-10〜18 の記録は VPS には元々存在しない」ことを確定（`analysis/vps-snapshot-20260710-verification.md`）．喪失実体は local-secondary 上の削除（同 escrow の最古生存 06-15 は，07 月中旬の cleanup 実行時の 30 日境界と整合）
- **Permanent guardrail introduced:** 全 host で `cleanupPeriodDays = 9999`（2026-07-21 owner 設定）．以後の収集は read-only escrow + sha256 manifest 登録（AGENTS.md 規則 1–2）で不変性を保証
- **Generalisable lesson:** agentic 開発ではセッションログが「実験ノート」に相当するが，開発ツールの log retention 既定値は研究記録の保全要件を満たさない．**プロジェクト開始時点で retention 設定とログ台帳を仕込むこと**が，事後のいかなる復元努力よりも安価である（本件の復元試行はスナップショット復元・全 sha256 照合まで行って収穫ゼロ）
- **Primary evidence:** `analysis/vps-snapshot-20260710-verification.md`（バックアップ tar sha256 `ad71e1a9…fda37` の全照合記録），EV-1681〜EV-2126（local-secondary escrow，最古生存 06-15 の実物），EV-0001〜EV-1633（vps escrow），`evidence/repository-snapshots/leray-hopf/commits.json`（06-10 init 27 commits）
- **Evidence type:** primary（喪失検証プロセス自体は escrow 実物・snapshot 全照合・Git 記録で完結）．なお喪失対象期間 06-10〜14 の作業内容自体は reconstructed（Git/GitHub 証跡のみ）としてしか扱えない — それが本インシデントの帰結である
- **Confidence of reconstruction:** high（喪失の範囲・非存在の証明は一次資料で確定．**削除がどの日にどのマシンで実行されたかのみ** mtime 整合からの推定で medium）
