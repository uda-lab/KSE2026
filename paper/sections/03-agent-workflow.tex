Figure~\ref{fig:author-interface} places the work in three parts above one
shared record: the author held final authority over scope and acceptance,
ChatGPT supported investigation, synthesis, and drafting without deciding,
and the agent harness carried out issue-scoped work without independent
authority. % CLAIM: CLM-012
Figure~\ref{fig:agent-harness} expands that harness; its controls were
introduced incrementally, including in response to the incidents in
Section~\ref{sec:incidents}, so the diagram reconstructs the end state. % CLAIM: CLM-007, CLM-009

The work ran on two local computers and an isolated development
container on a virtual private server (VPS), where many orchestration
sessions ran in parallel. Agents worked in separate Git worktrees but
shared the repository, the Lean build cache, and a memory ceiling of
3.42\,GiB, which made computing resources part of the harness. % CLAIM: CLM-007, CLM-009, EV-0247

\subsection{Author authority and the GitHub workflow}

A GitHub Issue (hereafter Issue) defined each unit of work and its
acceptance conditions. When a proposition could easily be overstated, a
separate statement card recorded its hypotheses, conclusion, and permitted
proof boundary, exposing the mathematical contract to review. % CLAIM: CLM-009

The main orchestrator assigned agents and checked their returned artifacts
without editing Lean files itself. A standing repository rule required every change to begin with an
Issue; the workflow was otherwise conventional. An implementing agent received its own branch and Git worktree and
returned a committed candidate through a PR, which could merge only after
the checks relevant to its changed artifacts had passed, an independent
reviewer had left an attributable result, and all review threads were
resolved.

Issue scope, review decisions, and merge authority were recorded in
repository and GitHub artifacts rather than only in an agent session; when
a different orchestrating model (Fable~5) took over through Google Cloud's
Vertex AI on July~2--3, it continued the workflow from those artifacts.
% CLAIM: CLM-003, CLM-007, CLM-009, EV-1681

Questions about mathematical meaning returned to the author and statement
card, while Lean errors and build failures returned to the implementing
worktree. During the large July refactor, the orchestrator first assigned
a read-only scout to inspect repository assumptions, then separate agents
to implementation, module inspection, and comparison of public
declarations. % CLAIM: CLM-007, EV-1669

\subsection{Checks selected by artifact}

\emph{Mathematical statement.}
An agent independent of the implementer checked whether the proposition
matched the intended mathematics and whether its hypotheses sufficed,
looking for concrete counterexamples near a boundary of validity before
proof search continued.
% CLAIM: CLM-005, CLM-007, EV-0925

\emph{Lean declaration and assumptions.}
The Lean build checked elaboration and type correctness,
\texttt{\#print axioms} recorded the assumptions of designated
declarations, and an import check kept experimental modules outside the
public root import. % CLAIM: CLM-009

\emph{Public declarations.}
Refactoring was checked against the preceding inventory of public
declarations, whether or not anything downstream used them, and against
statement text when exact preservation was required. % CLAIM: CLM-007, EV-1669

The PR recorded each check's outcome and the reviewer's identity and
result alongside the candidate, so a dispatched but unfinished review could
not stand in for completed assurance.
% CLAIM: CLM-007, CLM-009, EV-1669

\subsection{Worktree assignment, liveness, and computing resources}

Each Git worktree had one active implementing agent, and shared import
files had one designated writer. An apparent loss of contact did not by itself reassign the worktree,
since a replacement there could duplicate edits and builds; the
orchestrator first checked the agent's process state. % CLAIM: CLM-007, EV-2076, EV-1669, EV-0247

Heavy Lean builds shared a cache and ran under a global lock; before
starting one, the harness checked memory available to the whole container,
removed helper processes left by completed jobs, and under pressure
reduced Lean's thread count. % CLAIM: CLM-007, CLM-009, EV-0247

\subsection{Evidence and measured use}

Session records, Issues and PRs, build results, and release artifacts
were retained as separate sources, and claim identifiers connect the
paper's tagged claims to them. % CLAIM: CLM-009

From 2026-06-10 through the release on 2026-07-20, the collected logs
record at least 15.1M output tokens; joining adjacent events across gaps of
at most five minutes gives a coarse estimate of 199.1h of active session
time. Applying published API prices to that use gives \$6{,}973. Apart from
the Vertex AI phase below, the agents ran on subscription plans rather
than metered billing, so this is an API-price-equivalent estimate, not an
amount billed; both the token count and the estimate are lower bounds,
because some session records were lost. % CLAIM: CLM-002

The July 2--3 completion phase was the one phase billed per token rather
than by subscription. The provider export records JPY~54{,}868 for all
activity on that machine, while published API prices applied to the
project's logs give \$258.28 for its share. If the provider's aggregate
token metric measures the same token classes as the logs, the provider's
effective rate places that share at JPY~41{,}421--41{,}796.
% CLAIM: CLM-003, CLM-007

For incident analysis, six sessions selected for their reconstruction
value were coded independently of the formal result. They contain four
statement mismatches or weakenings, nineteen recovery actions, twelve
resource failures, and five worktree assignment conflicts, with no
unresolved mismatch between a runtime success report and the state on
disk. These counts describe the selected sessions, not rates. % CLAIM: CLM-004
