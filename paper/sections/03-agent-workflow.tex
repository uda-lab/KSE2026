The work ran across two local computers and an isolated development
container on a virtual private server (VPS). Many parallel orchestration
sessions used the VPS container. Agents worked in separate Git worktrees
but shared the repository, Lean build cache, and a memory ceiling of
3.42\,GiB. This setting made computing resources part of the harness rather
than background infrastructure. % CLAIM: CLM-007, CLM-009, EV-0247

\subsection{Owner authority and the GitHub workflow}

The scientific owner retained authority over theorem scope. A GitHub Issue
(hereafter Issue) defined each unit of work and its acceptance conditions.
When a proposition could easily be overstated, a separate statement card
recorded its hypotheses, conclusion, and permitted proof boundary. The
Issue bounded implementation. The statement card exposed the mathematical
contract to review. % CLAIM: CLM-009

The main orchestrator assigned agents and checked their returned artifacts
without editing Lean files itself. The repository skill
\texttt{github-driven-workflow} required every change to begin with an
Issue. An implementing agent received its own branch and Git worktree, then
returned a committed candidate through a GitHub pull request (PR). Direct
pushes to the main branch were prohibited. A PR could merge only after the
checks relevant to its changed artifacts had passed, an independent
reviewer had left an attributable result, and all review threads were
resolved.

The workflow made the orchestrator role independent of the model that
filled it. The project began using GitHub on June~19, and the first
documented independent PR review occurred on June~20 under an Opus
orchestrator. When Fable~5 became available again in early July, it assumed
the same role under the existing authority and merge contract.
% CLAIM: CLM-007, CLM-009, EV-2076, EV-0925

This workflow also separated the destinations of review findings.
Questions about mathematical meaning returned to the owner and statement
card. Lean errors and build failures returned to the implementing
worktree. During the large July refactor, the orchestrator first assigned a
scout that could inspect repository assumptions but not edit them, then assigned separate
agents to implementation, module inspection, and comparison of public
declarations. Inspection roles had no edit authority. % CLAIM: CLM-007, EV-1669

\subsection{Checks selected by artifact}

\emph{Mathematical statement.}
An agent independent of the implementer checked whether the proposition
matched the intended mathematics and whether its hypotheses were
sufficient. For statements near a boundary of validity, the reviewer
looked for concrete counterexamples before proof search continued.
Section~\ref{sec:incidents} contrasts a defect found by this procedure
before merge with one that remained until release preparation.
% CLAIM: CLM-005, CLM-007, EV-0925

\emph{Lean declaration and assumptions.}
The Lean build checked elaboration and type correctness.
\texttt{\#print axioms} recorded the assumptions of designated
declarations, and an import check kept experimental modules outside the
public root import. A full build was recorded for the release commit.
% CLAIM: CLM-009

\emph{Public declarations.}
Refactoring was checked against the preceding inventory of public
declarations. When exact preservation was required, the comparison also
covered statement text. This check was independent of downstream use and
therefore detected an unreferenced theorem omitted during refactoring.
% CLAIM: CLM-007, EV-1669

The GitHub workflow preserved these results with the candidate they
assessed. A review request alone was insufficient. The PR needed the
reviewer's identity and result. This prevented a dispatched but unfinished
review from being mistaken for completed assurance.
% CLAIM: CLM-007, CLM-009, EV-1669

\subsection{Ownership, liveness, and computing resources}

Each Git worktree had one active implementing owner, and shared import
files had one designated writer. An apparent loss of contact did not by
itself transfer ownership. The orchestrator first checked the agent and
its process state, because starting a replacement in the same worktree
could duplicate both edits and builds. % CLAIM: CLM-007, EV-2076, EV-1669, EV-0247

Heavy Lean builds shared a cache and ran under a global lock. Before
starting one, the harness checked memory available to the whole VPS
container and removed helper processes left by completed jobs. Under
pressure, it also reduced Lean's thread count. These requirements were
placed in standing agent instructions and repeated in dispatch prompts.
They did not depend on an agent recalling an earlier incident.
% CLAIM: CLM-007, CLM-009, EV-0247

\subsection{Evidence and measured use}

Session records, GitHub Issues and PRs, build results, and release
artifacts were retained as separate sources. Claim identifiers connect
paper statements to those sources, while reconstructed intervals remain
distinguishable from primary session evidence. % CLAIM: CLM-009

From 2026-06-10 through the release on 2026-07-20, the collected logs
record at least 15.1M output tokens, a cost of \$6{,}973 at published API
rates, and 199.1h of active engagement when adjacent events are joined
only across gaps of at most five minutes. These values are lower bounds
because some session records were lost or unavailable. % CLAIM: CLM-002

The July 2--3 completion phase occurred immediately after Fable~5 became
available again. Fable orchestrated that work through Google Cloud's
Vertex AI, with Opus agents used for some delegated tasks. The provider
export records a charge of JPY~54{,}868 for all activity on the machine,
while applying published API prices to the project logs gives
\(\$258.28\). If the provider's aggregate token metric measures the same
token classes as the logs, the project's share of the charge is
JPY~41{,}421--41{,}796. % CLAIM: CLM-003, CLM-007

For incident analysis, six sessions were selected for their
reconstruction value and coded independently of the formal result. They
contain four statement mismatches or weakenings, nineteen recovery
actions, twelve resource failures, and five Git worktree ownership
conflicts. No unresolved mismatch between a runtime success report and
the state on disk was found. These counts describe the selected sessions.
They do not estimate rates for the project or for agent systems in
general. % CLAIM: CLM-004
